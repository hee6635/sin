# 앱 만들기 노트 (언제쉬어에서 배운 것)

## 1. 사용자 성향 · 일하는 방식
- **한국어 · 쉬운 말 · 짧게.** 결과 먼저, 꼭 필요한 것만 쓴다. 긴 설명, 표, 반복 요약은 빼고 3~5줄로.
- **질문 ≠ 작업 지시.** 질문하거나 문제만 알려 주면 고쳐서 보관해 두고 "고쳐서 올릴까요?"라고 먼저 묻는다. "만들어 · 올려 · 고쳐서 올려 · 응"일 때만 올린다. (괜히 작업하면 비용 낭비라고 싫어함)
- **기획은 먼저 판단한다.** 좋으면 TODO에 저장한다. 보통이거나 별로면 이유와 대안을 말하고, 결정은 사용자가 한다. 이미 있는 기능과 겹치는지, 안 쓰는 사람 화면에 늘어나는지 꼭 따진다.
- **시안 먼저.** 모션은 사진이 아니라 **움직이는 영상(mp4)** 으로 보여준다. 고를 것이 있으면 번호를 붙인 여러 안을 한 장 · 한 영상에 담는다.
- **"다 확인했다"고 쉽게 말하지 않는다.** 무엇을, 어떤 방법으로 확인했는지와 못 본 것을 같이 말한다. (위아래만 재고 "다 됐다"고 했다가 좌우 폭 문제가 남아 신뢰를 잃은 적 있음)
- 사용자가 영상이나 기록을 보내면 프레임을 잘라서 정확히 본다(ffmpeg fps=6~30 + tile). 사용자 말이 맞을 때가 많다. 내 판단이 틀렸으면 바로 인정한다.
- **폰만 있는 사용자.** 컴퓨터가 필요한 일(서버 규칙 배포 등)은 미리 "사용자 몫"으로 표시한다. 방법은 둘: ① Firebase 콘솔 → Firestore → 규칙에 붙여 넣고 게시 ② Cloud Shell에서 `git clone -b 브랜치 …` → `cd sin/firebase` → `npx firebase-tools deploy --only firestore:rules --project 프로젝트`. 명령은 **한 줄씩 따로** 주고, 막힌 화면 캡처를 받아 고친다. (폴더가 없다는 오류 = 먼저 clone 해야 함)
- **방(대화) 옮기기.** 방이 길어지면 `docs/HANDOFF.md`를 올려 두고 새 방에 붙여 넣을 첫 문장 한 줄을 준다. 새 방에서 **브랜치를 꼭 지정**하게 한다. 두 방이 같은 브랜치에 올리면 push가 거절되니 먼저 `git pull --rebase` 로 합친 뒤 올린다.
- **빌드 아끼기.** 문서 · 시안(docs/ · design/)만 바뀌면 APK 빌드가 안 돌게 해 둔다(paths-ignore). 앱 수정은 커밋만 해 두고, 문서만 먼저 올려야 할 땐 순서를 바꿔(cherry-pick) 문서 커밋만 올린다. "만들어" 때 한 번에 올린다.
- **기능을 지우기 전에.** 바로 지우지 말고 ① 기본값만 바꾸고(새로 설치하는 사람만) ② 기존 사용자 화면은 그대로 두고 ③ 사용 통계로 쓰는 사람을 본 뒤 지운다. 업데이트했더니 화면이 바뀌었다는 불만이 가장 흔하다.

## 2. 좋아하는 UI
- **미니멀.** 회색 작은 설명 글을 쓰지 않는다. 꼭 알아야 할 것은 "이럴 땐 이렇게" 팁으로 따로 둔다. 상태 값(켜짐, 바뀜 등)만 남긴다.
- 토스 느낌: 회색 바탕에 흰 카드, 둥근 모서리(18~22px), 아이콘 칸(회색 둥근 사각형 + 선 아이콘), 줄(row) 단위 설정.
- **고르기**: 테두리 알약(고른 칸 = 흰 판 + 파란 테두리). 바꿀 때 흰 판이 늘어나며 미끄러진다. 모양은 바꾸지 말고 모션만 더한다.
- **스위치**: 물방울(동그라미가 늘어나며 미끄러지고 끝에서 살짝 눌림).
- 버튼: 저장 · 보내기는 알약 또는 동그라미 + Spring Pop. 아이콘은 뜻이 분명한 것(⊕, ✓, ⌄). 추가 버튼은 ⊕ 테두리 동그라미.
- 입력칸: 쓰기 시작하면 placeholder 글씨가 칸 위로 작게 올라가 남는다(누가 보는지 보이게). 전송 버튼은 글이 있으면 색이 아래에서 차오른다.
- 이름 입력칸: 회색 칸 + 안쪽 여백 14px, 글자가 칸 끝에 붙지 않게. 누르면 파란 테두리.
- 다크 모드도 같은 구조. 색은 CSS 변수로만.
- **새 아이콘은 앱에 이미 쓰는 아이콘과 같은 종류로 통일한다.** 넣기 전에 주변 화면의 아이콘을 먼저 보고 맞춘다 (언제쉬어는 선 아이콘 npi() — 색 이모지 ✏️를 넣었다가 "이모티콘 통일했는데 왜 갑자기 저걸로" 지적).
- **작은 배지(1/2 같은 숫자 표시)** 는 스티커 크기에 비례해 키우고 줄인다. 고정 글자 크기로 두면 좁은 화면에서 스티커보다 커진다.
- **설정 화면.** 자주 쓰는 것(근무 패턴 · 가족 · 알림 · 스티커 · 위젯 · 백업)은 첫 화면 **타일**(값 요약 한 줄)로, 한 번 정하면 안 바꾸는 것(화면 모드 · 글자 · 배경 · 달력 모양)은 안쪽 "화면" 페이지로, 정보 · 문의 · 지우기는 "도움 · 정보"로. 기능이 엉뚱한 곳에 숨어 있으면(알림 소리가 스티커 안 · 모양 조정이 개발자 화면 안) "한눈에 안 보인다"는 말을 듣는다.
- **잘 보이게 옵션("또렷하게")**: 파스텔 대신 진한 색 · 굵은 글자 · 칸 테두리(글자 대비 4.5:1). 바탕 칩 하나로 켜고, 앱 · 위젯 · 어두운 화면 모두 따라가게. 색을 처음부터 변수로 두면 쉽다.
- 같은 종류 글자는 크기를 맞춘다(예: "휴"가 "주/야"보다 작으면 어색하다는 말을 들음).

## 3. 좋아하는 모션 (원칙)
- **툭 바뀌는 곳이 없게.** 모든 상태 변화에 움직임이 있어야 한다. 단, 과하지 않게(0.25~0.45초 · 감속 곡선 `cubic-bezier(.2,.9,.25,1)`).
- 창 열기: **누른 자리(칸 · 카드)에서 커져 나오고, 닫으면 그 자리로 쏙.** 누른 자리가 없으면 아래에서 올라오고 아래로 내려간다.
- 페이지 이동: 옆에서 밀려 들어오고, 뒤로는 반대쪽으로.
- 날짜 · 달 넘기기: 손으로 넘길 때와 버튼으로 넘길 때 똑같이 옆으로 밀린다. 연달아 누르면 목표만 바꾼다(씹히지 않게).
- "오늘" 버튼: 다른 달에서 이번 달로 쓱 미끄러진 뒤, 오늘 칸 테두리에 은은한 빛이 한 바퀴 돌고 사라진다. 너무 강하지 않게.
- 접기 · 펼치기: 높이가 스르르. 화살표 ⌄는 펼치면 180° 돌아 ⌃.
- ＋ → ✕: 돌면서 바뀌고 아래 줄이 펼쳐진다. 반대로 하면 접힌다.
- 칸이 생기거나 없어질 때: 커지며 톡, 줄어들며 쏙. 아래 칸들은 미끄러져 자리를 잡는다.
- 글자나 폭이 바뀔 때(예: 휴무 → 야간 · 바뀜): 폭이 늘고 줄며 글자는 살짝 바뀐다.
- 토스트: 위에서 뒤집히며 내려오고, 새 알림이 오면 기존 것 위로 쌓인다.
- 진동은 알람 · 알림에만 쓴다. 버튼 진동은 넣지 않는다.

### 3-1. 홈 화면 위젯 모션
위젯은 **그림 한 장이 곧 프레임 한 장**이다. 프레임마다 화면을 새로 그리면 끊긴다.
- 그림은 **층 3장**만 미리 그린다: 바깥 틀 · 떠나는 달 칸들 · 들어오는 달 칸들. 프레임마다 위치 · 투명도만 바꿔 겹친다(프레임 하나 = 몇 ms).
- 진행은 **시간 기준**. 느린 폰에서는 늦은 프레임만 건너뛰고 속도는 그대로(슬로모션이 되지 않게). 프레임 사이 최소 간격 약 28ms.
- 중간 프레임은 `partiallyUpdateAppWidget`으로 **그림만** 바꿔 끼우고, 누르는 자리(PendingIntent)는 끝에 한 번만 전체 갱신.
- 새로 누르면 위젯별 "효과 번호"를 올려 이전 효과를 멈춘다(두 효과가 섞여 깜빡이지 않게).
- 위젯 그림은 약 70만 픽셀로 제한해 두면 프레임이 가볍다. 바탕이 반투명이면 층을 겹칠 때 바탕이 짙어지지 않게 "바깥 틀"과 "칸들"을 따로 그린다.
- 빛(테두리 한 바퀴)은 칸 테두리를 따라 꼬리를 끄는 선 한 줄이 시계 방향으로 도는 방식 + 테두리 전체가 살짝 빛났다 옅어지기.
- 컴퓨터 시험: 가짜 그래픽(shim)으로 같은 함수(겹치기 · 빛 그리기)를 돌려 프레임 PNG를 뽑아 눈으로 본다.

## 4. 버벅임 · 렉 — 겪은 문제와 해결 (중요)
1. **모션은 transform · opacity 만 움직인다.** backgroundColor, borderRadius, height 같은 것을 움직이면 폰이 메인 스레드에서 그려서, JS가 바쁜 순간 멈춘다.
   - 예외: 높이 변화는 짧게(0.32초) 쓰고, 무거운 작업과 겹치지 않게 한다.
2. **큰 창은 "껍데기" 방식으로 연다.**
   - 빈 판(껍데기)이 누른 칸에서 커지는 동안에는 아무것도 만들지 않는다.
   - 다 커져서 멈춘 뒤 진짜 창을 만들고, 두 프레임 뒤 껍데기를 걷어낸다.
   - 움직이는 도중 진짜 창을 처음 칠하면(첫 paint) 그 시간만큼 멈춘다. 멈춘 화면 뒤에서 칠하면 아무도 모른다.
3. **열리는 동안 · 열린 직후 1.2초는 뒤 작업을 미룬다.** 옆 달 그리기, 위젯 자료 읽기(약 100ms), 가족 자료 새로 받기, 다시 그리기(render) 등. 켜자마자 날짜를 여는 사람이 많아서 켤 때 작업과 늘 겹친다. 모션 막바지에 이런 작업이 몰리면 마지막 프레임이 끊긴다.
4. **처음 열 때는 가볍게.** 날짜 띠는 7칸만 그렸다가 도착 뒤 61칸으로 채운다. 다음에 누를 큰 창은 미리 만들어 둔다(예: 날씨 큰 창). 외부 자료(날씨 등)는 누르는 순간이 아니라 **앱을 켤 때 · 다시 앞으로 올 때 미리 받아 저장**한다(들어오는 길이 여러 개라 "첫 탭 뒤에 계산"은 길마다 붙여야 해서 빠뜨리기 쉽다).
   - 단, 빈 자리를 잡아 두는 방식은 높이가 0이면 뒤 카드가 밀려 "번쩍"한다. 차라리 처음부터 넣는다.
5. **반투명 판이 커지면 뒤 글자와 겹쳐 번쩍인다.** 판은 처음부터 불투명하게, 글자는 판이 거의 다 커진 뒤에 보여준다.
6. **추측하지 말고 폰에서 잰다.** 앱 안 개발자 메뉴에 "시작 기록"을 넣는다.
   - 무엇을 넣나: 켠 뒤 12초 + 창 열 때 3초 동안의 긴 작업, 화면 멈춤(프레임 간격 40ms 넘음), 함수별 시간(pfWrap), 손가락 닿음/뗌
   - 멈춘 이유: `PerformanceObserver('long-animation-frame')` → 계산(어떤 함수) · 배치 · 그 밖(그리기)으로 나눠 적는다
   - **복사 버튼**을 꼭 둔다(캡처는 귀찮아함)
   - CPU를 느리게 한 컴퓨터 흉내는 미세한 차이에서 틀렸다. 폰 기록이 정답이다.
7. **옆으로 미는(스와이프) 동안 touchmove를 preventDefault** 한다. 안 하면 브라우저가 끌기 멈추기로 다음 첫 탭을 먹어서 "두 번 눌러야" 된다.
8. **다시 그릴 때(innerHTML) 모션이 끊기지 않게.**
   - 그리기 전에 칸 높이 · 자리 · 폭 · 글자를 적어 둔다(종류+순번으로 짝 · 줄 이름은 글자로 짝).
   - 그린 뒤 옛 값 → 새 값으로 이어 붙이고, 새 칸은 0에서 펼친다.
   - 높이는 한 박자(rAF) 뒤에 재야 한다. 바로 재면 덜 그려져서 끝에 툭 튄다.
   - 폭이 늘어나는 동안 글자가 두 줄로 접히면 높이가 튀니 `white-space:nowrap`.
   - 스위치처럼 누르는 순간 다시 그리는 것은 change 대신 click에서 받는다. 떨어져 나간 요소에서는 change가 안 온다.
9-1. **같은 날짜 칸이 여러 개일 수 있다.** 옆 달 판을 미리 그려 두면 1~7일 · 말일 근처가 흐린 칸으로 한 번 더 있다. `querySelector`(첫 번째)로 고르면 화면 밖 칸을 움직인다 → 늘 **보이는 칸**을 골라 쓴다. ("1~7일만 톡이 없다"는 제보로 찾음 · 처음엔 엉뚱한 원인을 고쳤다가 되돌림)
9. 뒤로가기는 **가장 위에 보이는 것부터** 닫는다(elementFromPoint로 확인). 창 상태 플래그 순서로 정하면 아래 깔린 창이 먼저 닫힌다.
10. **폰 웹뷰는 컴퓨터 크롬과 다르게 글자를 그린다.** (겪은 일: 1/2 배지를 두 번 줄였는데 폰에서는 그대로 컸음)
    - 안드로이드 웹뷰는 **8px보다 작은 글자를 8px로 키운다**(최소 글자 크기). 컴퓨터에서는 작게 나와 못 잡는다. 앱에 "큰 글씨"(텍스트 확대) 설정이 있으면 그만큼 또 곱해진다.
    - 해결: 글자는 10px 같은 크기로 그려 두고 **배율(`scale`)로 줄인다.** 글자 크기가 아니라 상자 전체를 줄이므로 최소 글자 규칙을 안 받는다. 배율은 JS로 "실제로 그려진 글자 크기"를 재서 `스티커 크기 × 비율 ÷ 실제 글자 크기`로 정한다(큰 글씨 설정도 같이 보정). DOM이 바뀔 때마다(MutationObserver) · 다시 그린 뒤 다시 계산.
    - 시험: 컴퓨터 크롬을 `--blink-settings=minimumFontSize=8,minimumLogicalFontSize=8` 로 띄우면 폰 조건이 재현된다. **고치기 전 · 후를 같은 조건에서 숫자로 비교**한다(예: 배지 16.3×11.1px → 11.5×7.6px).
    - 교훈: "컴퓨터에서 줄었으니 됐다"는 확인이 아니다. 폰 조건을 먼저 재현한다.
11. **자리 판단은 짐작 말고 잰다.** "폰이면 명절 이름을 아래로"처럼 화면 폭으로 정하지 말고, "숫자 + 이름 + 스티커 2개가 한 줄에 들어가나"를 실제 폭으로 계산해 넣고/내린다. 재 보니 울트라(412)도 옆에 두면 스티커가 줄어들었다. 위젯은 위아래만 보지 말고 **가로로도** 겹치는지 본다(이름은 왼쪽 · 근무 글자는 가운데).

## 4-1. 자주 빠뜨린 것 (기능 하나에 "형제 화면"이 여럿)
- **같은 것을 그리는 곳이 여러 군데다.** 언제쉬어 달력: 내 달력 · 내 달력 보기(가족 것만 보는 폰) · 가족 달력 페이지 · 직접 추가한 가족 달력 · 위젯(한 달 · 1칸 · 2칸 · 7일) · 위젯 날짜 팝업. 새 기능을 내 달력에만 넣고 나머지에서 빠뜨린 일이 여러 번(오늘 빛 · 포스트잇 버튼 · 명절 이름 아래로 · 오늘 근무 색 · 할 일 완료 표시). **이 목록을 체크리스트로 두고 기능마다 전부 확인한다.**
- **누구 기준인지 먼저 정한다.** "폰 주인 기준"과 "지금 화면에 보이는 사람 기준"이 다르다. 남의 달력만 보는 폰은 내 근무표가 비어 있어서, 오늘 근무 색이 늘 기본 파랑이었다 → 보이는 달력 기준으로.
- **위젯은 따로 받은 데이터만 안다.** 앱에서 새 상태(할 일 완료 · 색 · 배경)를 만들면 위젯 데이터(JSON)에도 실어야 한다. 앱에선 줄이 그어지는데 위젯은 몰랐다.
- **위젯 전역 값은 그리는 순서에 따라 바뀐다.** 맨 윗줄을 나중에 그리면 오늘 색이 기본값으로 돌아가서, 그 뒤에 그린 빛이 늘 파랑이었다 → 효과는 "그 그림을 그릴 때의 값"을 같이 들고 다닌다.
- **새 페이지를 만들면 화면을 꼭 찍어 본다.** 줄 모양 CSS가 특정 목록(`.mlist .mi2`) 안에서만 먹게 되어 있어서, 새 알림 페이지 줄이 모양 없이 나왔다. 감싸는 틀을 바꾸면 다른 줄(스위치 설명)이 깨지기도 하니 둘 다 본다.
- **저장 데이터를 읽는 긴 한 줄에 `//` 주석을 넣지 않는다.** 그 뒤 설정이 전부 주석이 되어 글자 크기 · 테마 등을 못 읽을 뻔했다. 그런 줄엔 `/* */`만. 옛 데이터 시험이 잡아냈다.
- **처음 설치(저장 전) 상태로도 모든 화면을 연다.** 아직 없는 값(`S.widget` 등)을 바로 읽으면 그 화면이 멈춘다.

## 5. 시험 · 점검
- **옛 저장 데이터로 켜지는지**: 큰 작업 뒤 꼭 확인한다(normalize가 실패하면 데이터를 못 읽음).
- **판정 없는 스크립트는 시험 목록에 넣지 않는다**(`look/` 폴더). 늘 실패하는 시험이 섞이면 진짜 문제를 못 찾는다. 결과 파일 이름도 섞이지 않게 한다.
- 모션 전수 조사 도구 두 가지:
  - "모션 없음": 버튼을 다 눌러 보고, DOM이 바뀌는데 animate나 transition이 0이면 표시. 스크롤 애니메이션은 못 잡으니 따로 확인한다.
  - "툭 바뀜": 프레임마다 칸의 위치 · 높이 · **좌우 폭**까지 재서, 중간 값 없이 바뀐 것을 표시.
  - 둘 다 내 화면, 가족 화면, 아이 화면, 포스트잇, 팝업까지 **모든 화면**을 돌린다(빠뜨린 화면에서 꼭 나옴).
  - 다크 모드 주요 화면을 캡처해서 본다.
- 시험은 "모션 중 누르기" 같은 타이밍에 흔들린다. 기다림은 고정 시간보다 waitForFunction(될 때까지)으로 한다.
- Kotlin(안드로이드) 쪽은 SDK 없이도 컴파일 검사 도구로 "새로 생긴 오류"만 비교하고, 그리기 코드는 가짜 그래픽으로 컴퓨터에서 돌려 PNG로 본다.
- **시험이 실패하면 먼저 "원래부터 깨졌나"를 가린다.** 이전 버전을 따로 꺼내(git worktree) 같은 시험을 돌려 비교한다. 날짜를 오늘로 옮겨 돌리는 시험은 달 경계를 넘으면 깨진다(시험 쪽 문제).
- **화면 구조를 바꾸면 시험 도구도 같이 바꾼다.** 설정 안쪽 페이지가 아래 탭을 덮어서 옛 시험이 막혔다 → 시험 도구가 탭을 누르기 전에 열린 페이지를 닫게(폰의 뒤로가기와 같음).
- **시계를 멈춘 시험이 시간 버그를 드러낸다.** 폰 시각과 서버 시각을 비교하면 어긋난다 → "들어오기 전에 쓴 메모"처럼 순서를 따질 땐 같은 시계(폰 시각끼리)로 비교한다.
- 가족 기능은 에뮬레이터(auth · firestore · functions)로 폰 여러 대를 띄워 끝까지(초대 → 쓰기 → 알림 기록 → 나가기) 돌린다. 푸시는 보내지 않고 기록(`__pushlog`)만 남기게 해서 "누구에게 · 무슨 글이" 갔는지 확인한다.

## 6. 구조
- 처음부터 파일을 나눈다: `index.html`(뼈대 + 오류 안전망) · `app.css` · `js/*.js`. 한 파일이 1만 줄을 넘으면 고칠 때마다 다른 곳이 깨진다.
- 서버와 앱이 같은 계산(예: 날씨)을 쓰면 한 파일을 양쪽에 두고, 시험으로 "똑같은지" 확인한다.
- 올리기는 작업 브랜치 하나에만 하고, 본 브랜치는 마칠 때 합친다. 버전은 올릴 때마다 하나씩 올린다. HANDOFF(최신이 위) · TODO(✅)를 같이 고친다.

## 7. 가족(서버 연결) 설계 교훈
- 익명 로그인 번호가 방장 칸의 id라서, 앱 로그인 정보가 사라지면 같은 방으로 못 돌아간다. 복구 길(새 방 + 가족이 새 초대 코드로 옮기기, 구글 로그인 복원)을 처음부터 둔다.
- **연결을 지우는 코드는 두 번 확인한다.** 서버에서 내 칸을 한 번 못 찾았다고 바로 해제하지 않고, 5분 넘게 계속일 때만 해제 + 일정 시간 뒤 자동 재확인. 끊긴 뒤에는 안내 카드를 보여준다.
- 서버 규칙(firestore.rules)을 바꾸면 **배포는 따로** 해야 한다(앱을 올려도 안 바뀜). 규칙 시험(에뮬레이터)을 같이 돌리고, 배포가 필요하다는 것을 사용자에게 말한다.
- **방장 없이 모두 같은 권한**이 튕김 사고에 강하다: 누구나 초대 · 누구나 나가기 · 마지막 사람이 나가면 방이 없어짐. 내보내기는 다수결(내보낼 사람을 뺀 나머지의 절반 넘게, 30일 넘게 안 온 사람은 계산에서 뺌 · 7일 안). 잘못 초대는 초대한 사람이 24시간 안에 혼자 되돌림.
- **규칙은 옛 버전 앱도 계속 되게 바꾼다**(옛 경로를 남겨 둠). 순서는 "규칙 · 함수 배포 먼저 → 폰 업데이트". 반대로 하면 새 앱이 막힌다.
- **비용**: 많은 옛 데이터(다시 들어올 때 옛 메모 수백 건)는 한 건씩 올리지 말고 사람당 문서 하나로 묶는다. 읽는 쪽은 구성이 바뀔 때만 한 번 읽는다. 무료 횟수 · 알림은 "옮긴 것"이면 건너뛴다.
- 규칙에서 "한 번에 +1"을 확인하는 묶음 쓰기는 문서 하나씩만 된다(여러 개를 한 묶음에 넣으면 +N 이라 거절). 문서 id로 읽기를 막는 규칙(내보낼 사람은 표를 못 봄)은 목록 조회가 안 되니 문서마다 따로 듣는다.
- 남이 쓴 데이터(나간 사람의 메모 등)는 앱이 못 읽어서 못 지운다 → 정리는 서버 함수가 한다.
- 알림 문구엔 내용을 넣지 않는다(이름 · 날짜 · 포스트잇 제목만). 체크 같은 잦은 변화는 알림 대신 작은 점.
